## 1. 报告定位与方法

### 1.1 判定原则（本报告的操作化排序）

速记第 364–380 行给出课程的五条设计原则：**简洁性**（避免冗余构造，易学易实现）、**可读性**、**可写性**、**可靠性**（原文：「不要指针，防止内存泄漏（类型安全，行为可预测 —— 错误尽可能在编译器暴露）」）、**范式与演进**（原文：「需要面向对象，做一种简化」，并注明 `struct in rust` / `interface` / `trait`：*mix-in 混入，而不是继承*）。

本报告把它们操作化为可执行的排序：

```
简洁性  >  可读性 ≈ 可写性  >  可靠性  >  可实现性
```

- **简洁性**优先，具体含义是「能不新增关键字、能不新增语法就不新增」。§1.4 的关键字表已经封版（速记第 40–130 行的逐项裁决 + 后续补充确认），所以后半部分的一切决定都在「不新增关键字」的硬约束下做（`yield`/`async`/`await`/`static` 恰好都已在表内，这是第 8 部分能定稿的前提）。
- **可读性 ≈ 可写性**，两者冲突时按「读代码的次数远多于写代码的次数」偏向可读性；**可靠性**按老师原文理解为三点：类型安全、行为可预测、错误尽量在编译期暴露。本报告里它最重的两次出场是 A-5（无向下转换 ⇒ 无看错类型的 UB）与 C-1（无并行 ⇒ 无数据竞争）。
- **可实现性是本报告加的最后一位**：它是**下限**而非优化目标。一个决定如果让 `nvc`/`nvld` 的实现量超出课程预算，即使更简洁也要让步（C-1 没选「多线程 + 内存模型」有很大一部分是这个理由）。**这条添加本身需要老师确认。**
- 「范式与演进」是**元原则**，用于在候选之间打破平局：A-6 选 Python 引用模型而非 C++ 值模型、A-1 用单继承 + 组合而非多继承，都引用它——速记第 380 行「`trait`：mix-in 混入，而不是继承」说明老师对「继承」的态度本就是倾向混入。

### 1.3 「已定 / 排除 / 未定」三态的意义

`✔` / `✗` / `?` 的区分是这份报告最想强调的一点：

- `✔` **已定**：有条款、可测试、可作为实现依据；`✗` **排除**：**讨论过并主动放弃**，必须附理由与替代方案。把 `✗` 写成 `?` 的代价是：下一版会把已否决的方案重新讨论一遍。
- `?` **未定**：**还没想清楚**，必须附「**为什么先不定** / **不阻塞什么** / **暂用假设**」三问的答案。把 `?` 写成 `✔` 的代价更严重：实现者会以为有保证。

## 2. 类部分的取舍（A-1 … A-13）

### A-1 单继承，取代速记的「多继承用 `,` 隔开」 `⚠️ 与速记冲突`

**冲突原文**（逐字，速记第 201 行）：
> `10. class tiger <- public felid继承语法，多集成用`,`隔开`

（「多集成」按输入错误读作「多继承」；此行是速记里**唯一**提到多继承的地方，且没有给出语义，只给了分隔符。）

**这条为什么不算已定结论**：
- `nova-spec.md` §9.1 第 3 项把「`<-` 继承的完整规则：继承处的 `public` 含义、**是否多重继承**」明确列为**未定**；`01-语言设计.md` §10.A 第 4 条提出同一个问题。也就是说：当时**没有拍板**多继承，只留了一条语法倾向。
- 同一份速记第 380 行写的是「`trait`：mix-in 混入，**而不是继承**」——老师对继承本身的态度是倾向混入。两条放在一起看，第 201 行更像是一条**随手记下的语法备选**，而不是语义承诺。
- 即便如此，正文也**不能默默丢掉它**：丢掉一条老师写过的语法，在课程评审里等价于「没看见」，所以必须逐字引用 + 给出翻盘代价（见下）。
**候选**：

| 候选 | 布局可预测性 | 名字歧义 | 实现量 | 与「简化」原则 |
|---|---|---|---|---|
| ① 单继承 + 组合（选定） | 高（一个 vptr、一条链） | 无（链上唯一） | 低（§6.11 一套槽位规则） | 最简（组合代替第二基类） |
| ② 单继承 + 接口 / 混入 | 高（接口不占存储） | 需定接口方法冲突规则 | 中（新关键字或新声明形式，§1.4 已封版） | 好，但需新语法 |
| ③ 多继承（`<- A, B`，速记方案） | 低（多 vptr、多子对象） | 高（菱形、`super` 指谁、字段撞名） | 高（多表槽位复用 + 多 vptr 切换） | 差 |
| ④ 多继承 + 虚继承 | 最低 | 最高（虚拟基类共享子对象） | 最高 | 最差 |
**取舍**：① 与 §6.11 取向一致——A-3 的二进制兼容规则建立在「一个对象一套槽位视图」上，多继承会让「在继承链中间插入类是否兼容」这类问题无法用一句话回答；② 无 `interface`/`trait` 时「多个能力」用**组合**（把另一个对象作为字段）表达，`nova-spec.md` §2.3 的引用语义让组合的转发成本很低（不会拷贝）；③ 菱形基类在无 RTTI（A-5）、无虚继承的前提下**没有干净的语义**；④ 速记第 380 行的元原则站在这一边。
**选定**：单继承（§6.6 [3]），并列入排除项（§6.12 [1]）。`<-` 后的访问说明符必须显式写出（§6.6 [2]），其含义由 §6.6 [4] 的降级表定稿——这也销掉了 `nova-spec.md` §9.1 第 3 项。
**代价 / 风险**：
- 「多个能力」只能单链继承或组合；**组合会带来转发样板**（本语言无默认参数、无属性糖，§6.12 [11][12]），可写性有损失；没有接口 ⇒ 无法表达「这个类承诺提供这组方法」；与 A-13（无抽象成员）叠加后，「契约」在语言层面完全缺失。
- 若后续要补 `interface`/混入，需要在 §6.11 预留布局（接口不占存储、无需 vptr 位）；**本版本没有预留**，将来是加法而不是改写（风险可控）。

**若老师坚持多继承，改动清单与代价**（逐条款）：

1. §6.6 [3]「只允许单继承」→ 基类列表；[2] 访问说明符逐个写；[4] 的降级表按每个基类独立计算。
2. §6.6 [7] `super` 引用直接基类 → 需要消歧形式（如 `super.基类名::成员`），并新增语法 ⇒ §6.14 的 `super_access` / `super_call` 产生式重写。
3. §6.3 [2] 字段在**整条继承链**唯一 → 改为「跨所有基类子对象链唯一」，并规定菱形下的同名字段一律格式错误（除非引入虚继承，即候选 ④）。
4. §6.11 [1] 的布局「vptr 置偏移 0 **且只有一个**」**直接冲突**，整条重写：每层基类子对象按列表顺序 + 每个多态基类一个 vptr（或首基类共享 vptr 的 Itanium 方案）。连带 A-3 整条取舍作废。
5. §6.11 [2] 的 `align`/`size` 公式要加入基类子对象与多 vptr。
6. §6.11 [7] 的方法表从「一张表、基类先」改为「每个基类一张表 + 跨表槽位复用规则」，`override` 复用槽位的算法重写；「二进制兼容规则表」需要重写（A-3 的代价表失效）。
7. §6.7 [6] 构造期间分派：从「一个 vptr 加临时切换」变成「多个 vptr 逐个切换」。
8. §6.5 [6] 步骤 ② 与 [9]「第一条语句」：改为按基类列表顺序、且所有基类构造调用必须位于函数体最前。
9. §7.7 [7] 导出元数据、§7.8 [11] ABI 覆盖范围都要加「多基类布局」。
10. §6.12 [1] 删除；附录 A / D 的状态表与术语表更新。

**代价估计**：第 6 部分里 §6.11 全节 + §6.6 / §6.7 重写，EBNF 改 `inheritance`，且需要一次课确认菱形语义；与 A-3「二进制兼容优先」的取向正面冲突（多继承下兼容性无法用一张短表讲清）。
**回滚点**：§6.6 [2][3][4][7]、§6.5 [6][9]、§6.7 [6]、§6.11 [1][2][7]、§6.12 [1]、§6.14 `inheritance` / `super_access` / `super_call`。

### A-2 隐式虚函数（所有可分派成员函数天生可重写，无 `virtual`）
**候选**：① C++ 式显式 `virtual`；② 默认全部可重写（选定）；③ 只有写了 `override` 的函数才进入方法表；④ 默认不可重写 + 显式 `virtual`。
**取舍**：① 与 ④ 都要新增关键字，而 §1.4 关键字表已封版，且表里**本来就没有** `virtual`（速记第 40–130 行的逐项裁决里也没有）；③ 会让「基类先写、派生类后写」产生 ABI 差异——同一个基类函数在「有派生类重写」与「没有」两种情况下槽位分配必须一致，否则 §6.7 [7] 的跨编译单元一致性无法保证，因此 ③ 不可取；② 与已有的 `override`（§6.7 [1][2]）配合后语义闭合：**「签名相同必须写 `override`」**这一条只有在「所有可分派函数都天生可重写」的前提下才自然。
**选定**：§6.7 [4][5]——所有 `public` / `protected` 且非 `static` 的成员函数天生可重写；`private` 与 `static` 不参与（静态绑定）。
**代价 / 风险**：
- 动态分派有间接开销，且**无法关闭**（没有 `final`，§6.12 [4]）；性能敏感的库代码无处优化。
- 基类新增一个「恰好同名的函数」会**静默改变**派生类已有函数的意义：若签名恰巧相同，派生类的旧函数变成「漏写 `override` 的重写」⇒ 格式错误（这是好事，会报错）；若签名不同，则变成 §6.6 [8] 的**遮蔽**——派生类的重载集合被整体遮蔽，基类版本要用 `super.` 才能调用。这条遮蔽规则是 C++ 的著名坑，靠文档说清（§5 ① 已列为接口风险）。
- 无法表达「这个函数不能被重写」（与 A-13 是同一缺口的另一面：基类既不能强制重写，也不能禁止重写）。
**回滚点**：§6.7 [4][5]、§6.2 [9]（「访问级别不影响可重写性」的表述）、§6.14 `method_decl`（若改为显式 `virtual`，产生式要加修饰符）。

### A-3 `vptr` 置偏移 0 + 方法表槽位规则（二进制兼容优先）
**候选**：

| 候选 | 向上转换开销 | 派生类字段偏移稳定 | 空类大小 | 原生包互操作 |
|---|---|---|---|---|
| ① 无 vptr，类型标签 + `switch` 分派 | 0 | 不适用 | 0 | 最差（要传标签） |
| ② vptr 置**偏移 0**（选定） | 0（同一地址，无需调整） | 稳定（基类字段是前缀） | vptr 宽度 | 好（无可分派函数的类可按值传，C++ 侧声明 `vptr` 占位槽即可，§7.8 [6]） |
| ③ vptr 置对象**尾部** | 需要指针调整或负偏移寻址 | 不稳定（基类尾部被占用） | vptr 宽度 | 差 |
| ④ vptr 指向类型描述符，槽位在描述符里查 | 0 | 稳定 | 指针宽度 | 最差（多一层间接） |
**取舍**：① 与「二进制兼容」（`nova-spec.md` §2.2「关注二进制兼容：跨版本、跨架构」；速记第 203–205 行同）根本冲突——标签分派把类型集合写死在每个调用点；③ 破坏「基类子对象在派生类对象中的偏移为 0」这一唯一能让**隐式向上转换零开销**的性质（§6.7 [8] 要求向上转换隐式且恒安全）；④ 多一层间接且类型描述符本身要版本化。② 还有一个隐性收益：`array` / `string` 归结为类类型（§2.1、§3.1）后可以共用同一套「对象头」假设。
**选定**：§6.11 [1]（单 vptr、偏移 0、跨访问组不变）、§6.11 [7]（槽位规则：沿继承链从最基类到 D，**基类先、声明顺序在后**；`override` 复用基类槽位；新增函数（含新增重载）追加新槽位；`static` / `private` 不占槽位）；§6.11 [3]（构造期间的分派实现方式由实现选择，但不得改变可观察语义）。
**代价 / 风险**：
- **vptr 宽度成为阻塞实现的未定项**（§6.13 第 1 项；附录 B-1 第 1 项）：对象布局的具体字节数、原生包按值传递的 `struct` 对应都依赖它；空类不再为 0 字节（见 A-12）。
- §6.11 [7] 的兼容表有一处**只对叶子类成立**（本报告识别的正文不一致，见 §5 ②）：对「在类末尾追加字段 / 追加成员函数」两行而言，若该类在已编译代码里有派生类，追加会让派生类的字段偏移或槽位**整体位移**，因此不兼容。建议在该表下补一句限定：「仅当该类在已编译模块中不作为任何类的基类时成立」，或把这两行改为「在**最派生类**末尾追加才兼容」。
- 「在继承链中间插入一个类」不兼容，需要给用户明确的版本演进指导（把新类插在链尾、或让新基类只带新方法）。
- 附录 F-2 第 4 项把「方法表内的具体排列（在 §6.11 [7] 规则内的实现细节）」列为**实现定义**：槽位**顺序**的规则是 ABI，但生成规则必须由实现文档化，供 `nvld` 与原生包对齐；这给了实现一点自由度，也把「跨编译器单元一致」的责任明确交给了实现。
**回滚点**：§6.11 [1][2][3][7]、§6.13 第 1 项、§7.8 [11]、附录 B-1 第 1 项。

### A-4 禁止字段隐藏（派生类不得声明与基类同名的字段）
**候选**：① C++ 式允许隐藏（同名遮蔽，`Base::x` 访问）；② 整条继承链字段名必须唯一（选定）；③ 允许隐藏但要求写 `override`（把 `override` 用在字段上，语义怪且与 §6.7 [2] 的签名判定不搭）。
**取舍**：① 会让「裸名 = 一个确定的存储位置」不再成立（§6.4 [3] 第 2 步「本类及其基类的成员」将命中两个位置），并且让「对象大小 = 各字段之和」这句解释失效；② 换来的是：字段访问恒为静态偏移（§6.3 [7]）、布局可用一句话解释（§6.11 [1]）、`nvc` 不需要「按声明类型选字段」的规则。可写性的损失很小：需要新语义时改名字或用重写成员函数（§6.3 [2] 的注已写明）。
**选定**：§6.3 [2]（整条继承链唯一，违反者格式错误）、§6.6 [9]（在继承章重述）；§6.12 未新增条目（这是条款而非排除项）。
**代价 / 风险**：
- **跨版本源码兼容的坑（本报告强调）**：基类**新增**一个字段时，若某个已存在的派生类恰好有同名字段，派生类从「合法」变成「格式错误」。这不是布局问题，而是源码兼容问题，且只在两处代码同时升级时才暴露。缓解：新字段用不容易撞的名字（如加前缀）；在 §7.7 [7] 的导出元数据里本来就带字段名，`nvc` 可以给出精确诊断。
- 与 C++ 的习惯相反，迁移者会觉得束手束脚（文档成本）。
**回滚点**：§6.3 [2]、§6.6 [9]、§6.4 [3]（若放开，裸名解析要加层级规则）、§6.14 `field_decl`。

### A-5 禁止向下转换、无 RTTI
**候选**：① C++ 式 `dynamic_cast` + RTTI；② 不提供向下转换（选定）；③ 提供运行时类型检查 `type(obj) == 类名`；④ 在 `match` 上做类型模式（需要类型作为值）。
**取舍**：决定性理由不是实现量，而是**表达力**——在「无异常 + 无可空类型（§8.9 [1] 注引 §1.5：`none` 是 `void` 的值，不是空的可选值）」的语言里，向下转换**失败无法表达**：C++ 的 `dynamic_cast` 失败返回空指针，Nova 没有空引用；抛异常则语言无异常。③ 与 ④ 都要求「类型」能作为一等值参与比较，等于引入受限反射，与 §6.12 [10]「本语言没有运行时类型信息」冲突。安全性上，② 顺带消掉了「看错类型导致的 UB」这一整类错误（符合速记第 372 行的可靠性原则）。
**选定**：§6.7 [8]（向上转换隐式、向下转换不提供）、§6.11 [8]（`type()` 只做「派生 → 基类」，不做类 ↔ 值类型）、§6.12 [8][10]。
**代价 / 风险**：
- 这是**真实的能力缺口**而不是风格选择：当调用方需要访问派生类**特有**的字段或函数时，语言里没有合法途径。替代只能是把差异做成基类的 `override` 成员函数（多态），或者重新设计类型层次；与「无接口/无抽象成员」（A-13）叠加后，基类必须预先声明所有可能用到的操作，否则派生类的差异无法被外界使用。
- 与 `type()` 的边界（§6.11 [8]）需要在《表达式》章节回填「类类型之间只有向上转换」这一条，否则 `type()` 的规则在类型章与类章之间会不对称。
**回滚点**：§6.7 [8]、§6.11 [8]、§6.12 [8][10]、§6.9（若引入类型相关钩子）。

### A-6 引用语义 + 无隐式拷贝 + 显式拷贝构造函数 `⚠️ 与速记次级冲突`

**冲突原文**（逐字，速记第 287、289、291 行）：
> `所有类型值传递，可以使用&表示引用传递`
> `> a = 2; b = a;`
> `所有类型上述赋值就是创建新对象b`

与之相对的已定结论：`nova-spec.md` §2.3「复杂类型（数组等）**传引用**（参照 Python 模型）」；而 §2.5「拷贝」记为 `?` **暂缓**；速记的这句在 `01-语言设计.md` §2.3 里已被标注为「⚠️ 此条**暂不作为定论**，等实现编译器阶段再定」。所以这是**速记 vs 规范 + 速记自身**的双重矛盾，正文选边时必须说明。
**候选**：① C++ 值语义 + 隐式拷贝构造；② Python 引用语义 + 复制必须显式（选定）；③ 混合：值类型隐式拷贝、类类型引用；④ Rust 移动语义（本语言有 GC，移动语义没有存在理由，排除）。
**取舍**：② 与 `nova-spec.md` §2.3 已定结论一致（复杂类型传引用），也与「数组作为返回值返回引用」一致（§2.3）；更重要的是它**不需要先解开 §2.5**：本部分不引入任何隐式拷贝规则，只声明「引用绑定是默认语义、复制必须显式构造一个对象」，于是 §2.5 可以继续悬着——这是把「暂缓项」变成「不阻塞项」的样板。③ 会在类类型与值类型之间划一条隐含分界，而 §2.1 的分类本来就已经这么分了，所以 ③ 其实与 ② 等价，只是措辞问题；正文选 ② 的措辞是为了让「类类型」一章的规则自洽。
**选定**：§6.5 [10]（类类型是引用语义：变量、字段、实参保存引用）、§6.5 [14]（无隐式拷贝；需要副本时显式声明拷贝构造函数 `__constructor__(other: &vec2)`）、§6.5 [15]（`==` / `<>` 比较对象身份，内容相等用普通成员函数）。
**代价 / 风险**：
- 隐式共享导致的别名 bug 是新手最常见的错误；而语言**没有 const 成员函数**（§6.13 第 3 项未定）可以标注「这个方法不改对象」，所以类型系统无法表达「只读访问」。这是 A-6 最实质的可靠性代价；类类型字段不能取「零值」：§6.3 [4] 的字段清零只对值类型给出确定结果，类类型字段必须在构造函数体结束前被赋值（§6.5 [6] 步骤 ① 的清零对类类型不构成可观察值）。
- 显式拷贝构造函数依赖重载（A-10）与 `&T` 参数（§2.4）；`&vec2` 与 `const &vec2` 的差别又依赖 §9.1 第 1 项的未定语义；与速记「所有类型赋值创建新对象」正面冲突 ⇒ 需老师确认（列入 §5 ① 的次级清单）。
**回滚点**：§6.5 [10][14][15]、§6.3 [4]、§6.12 [9]、附录 C 第 14 项（`nova-spec.md` §2.5 回填）；若改为值语义，§6.11 的布局、§7.8 [5][6] 的传参约定、§6.5 [6] 的构造顺序都要连带重写。

### A-7 无析构函数 + 非移动 GC
**候选**：

| 候选 | 谁负责释放 | 回收时机 | 与 §2.4 `&` 引用 | 外部资源 |
|---|---|---|---|---|
| ① GC（追踪式，或**带循环收集**的引用计数）+ 无析构（选定） | 运行时 | 不确定 | 要求对象**不可移动** | 靠显式 `close()` |
| ② 手动 `delete` | 用户 | 确定 | 无要求 | 靠析构 |
| ③ 引用计数 + `__destructor__` 钩子 | 运行时 | 近似确定 | 无要求 | 自动 |
| ④ RAII / 作用域析构 | 词法作用域 | 确定 | 无要求 | 自动 |
**取舍**：② 已被课程排除（「不要 `new` / `delete`」，速记第 120 行）；④ 需要析构 + 确定时机，与 GC 共存会给出「析构可能在作用域结束时、也可能不」（因为有共享引用）；③ 看起来最诱人，但一旦把析构钩子写进语义，实现就必须能回答「循环引用怎么办」，从而被迫加收集器，等于把实现路线锁死。**纯引用计数在本版本被明确排除**（§6.5 [13]：类字段可成环，纯计数会漏收），因此 ① 的合法实现只有「追踪式」或「引用计数 + 周期收集」。① 的关键约束是**不可移动**：§2.4 的引用是别名（`let &a = c;`），§7.8 的原生包按对象地址传参（§7.8 [5][7]），两者都要求对象地址在生存期内稳定——因此压缩式 GC 被排除，同时也免掉了 GC 句柄表/写屏障的一部分复杂度。
**选定**：§6.5 [13]（运行时自动回收；三条硬约束：最终回收、**不得移动**、回收元数据不属于 §6.11 的对象布局）、§6.9 [5]（不定义析构钩子：提供析构只会给出「确定的回收时机」这一错觉）、§6.12 [7]（排除 `delete` / 手动释放）。需要释放外部资源时用显式成员函数（如 `close()`）并由调用者负责。
**代价 / 风险**：
- 外部资源（文件、句柄、原生内存）没有自动释放点，**忘记调用 `close()` 没有任何提示**；与 C-9（无错误传播通道）叠加后，资源泄漏连报告都没地方报。
- 非移动 ⇒ 不能用标记-压缩式 GC，长期运行的程序可能有碎片；同时实现可在「追踪式」与「带循环收集的引用计数」之间选择，而引用计数的「即时回收」会让「回收时机不确定」在不同实现间表现不同 ⇒ 实现**必须**在文档中声明所采用的算法（已登记为 §6.13 第 2 项 / 附录 B-1 第 2 项）。
- 生成器被 `break` 放弃时，挂起状态由运行时回收且**不触发用户代码**（§8.4 [9]、§8.8 [5]）——这与「无析构」是同一决定在两处的体现；`__to_string__` 之外的钩子（§6.13 第 4 项）里不能有「生命周期钩子」，将来要加也要受这条约束。
**回滚点**：§6.5 [13]、§6.9 [5]、§6.12 [7]、§6.13 第 2 项、§7.8 [7]（所有权条款）、§8.4 [9]、§8.8 [5]。

### A-8 构造顺序与显式 `super`（含基类无参构造可省略的例外） `⚠️ 边界扩展`

**已定约束**：`nova-spec.md` §6「**构造函数不自动调 `super`，必须手动显式调用**：`super.__constructor__("tiger");`」；`01-语言设计.md` §2.5 与 §8.4（`inherit.nova:20`）已核实示例与规则一致。
**候选**：① 完全严格（任何情况下都要写 `super.__constructor__(...)`，无参也要写 `super.__constructor__();`）；② 完全自动（有基类时自动调用其无参构造，像 Java/C++）；③ 严格 + 一个例外：基类存在无参构造时可省略（选定）。
**取舍**：① 最忠实于已定结论，但会把样板固定下来（每个派生类构造函数第一行都要写一次 `super.__constructor__();`），与「简洁性/可写性」有小摩擦；② 直接违反已定结论（「不自动调 super」），不可取；③ 只放宽到「无参构造」这一种情况——此时省略与写全**语义完全相同**（调用的都是那个唯一的无参构造），不存在「调错基类构造」的风险，也不存在「隐式调用带参构造」的可能。等价性使 ③ 可以被解释为对已定结论的**边界扩展**而不是推翻。
**选定**：§6.5 [6]（顺序：清零 → 基类构造 → 本类字段初值（按声明顺序）→ 本类构造体 → 完成）、[7]（不得自动调用，必须显式）、[8]（基类有无参构造时可省略，省略等价于体首调用）、[9]（显式 `super.__constructor__(...)` 必须是构造函数体的第一条语句）。顺序本身与 C++ 的「基类 → 成员 → 函数体」一致，并额外固定了「清零」这一步（§6.5 [6] 步骤 ①），供 `nvc` 与调试器依赖（§6.5 [9] 的注）。
**代价 / 风险**：
- 这是本报告**唯一**一处与 `nova-spec.md` 已定结论的边界摩擦，**必须请老师确认**（列入 §5 ① 次级清单）；若老师要求严格 ①，改法很小：删 §6.5 [8]，把示例补上 `super.__constructor__();`；例外让「是否调用过基类构造」不再能从调用点一眼看出（可读性的小损失）；实现上需要把「省略」归一化为「在函数体最前插入一条调用」。
- §6.5 [11]（构造期间把 `self` 传出后接收方不得在构造完成前访问，违反者 UB）与 §6.7 [6]（构造期间按**正在构造的类**分派）联合定义了「对象在任何时刻都处于确定的构造阶段」；UB 这一档没有诊断能力，只能靠文档（与 A-5 的无 RTTI 一起，构成「构造期安全靠约定」的现状）。
**回滚点**：§6.5 [7][8][9]、§6.6 [7]（`super` 的用法）、§6.14 `super_call`。

### A-9 `static` 定稿与常量初值

**已定/未定**：`nova-spec.md` §9.3 第 1 项「`static` 成员语法（关键字存在但无用例）」——正文 §6.8 销掉它。
**候选**：① 不要静态成员（连关键字一起删）；② 类级静态字段 + 静态函数，用 `::` 访问（选定）；③ 用模块级变量代替静态字段（但顶层可执行语句已被 §7.1 [3] 禁止，模块级 `let` 也无处安放）；④ 静态字段允许非常量初值 + 引入模块初始化函数。
**取舍**：② 复用已有的 `::` 语法（§7.4 [3] 的表里 `类名::静态成员` 一行），**零新增语法**；③ 与 B-4 冲突；④ 会把 B-4 的全部收益（无初始化顺序问题、循环 import 安全）一次性丢掉，与「简洁性」和「可靠性」都不合。`static` 的额外价值在于：本语言**没有枚举**（速记「枚举：不要」），`static const` 字段是唯一能表达「具名常量集合」的手段（例如错误码），这一点在 C-9 里会被再次用到。
**选定**：§6.8 [1]（`static` 写在字段或函数声明之前）、[2]（静态字段每个类一份，初值**必须是常量表达式**⇒ 不存在静态初始化顺序问题）、[3]（静态函数无 `self`，不得裸名访问实例成员）、[4]（用 `::` 访问；用对象访问静态成员为格式错误）、[5]（受访问组限制）、[6]（不占对象存储、不占方法表槽位、不参与重写）。
**代价 / 风险**：
- 静态字段不能由运行时计算得到（`static cache: int = compute();` 是格式错误）。想表达「第一次使用时初始化」只能自己写 `if` 标志位；`[4]` 禁止 `c.bump()` 这种「看起来像实例调用」的写法，迁移者会觉得别扭，但换来的是静态/实例访问在源码里完全可分辨。
- 常量表达式初值让「静态字段互相引用」的初始化顺序问题彻底消失（§6.8 [2] 的注），代价是**没有可变的模块级状态**（与 B-4 是同一枚硬币）；常量表达式的完整定义落在《表达式》章节，本部分只用了它的存在（接口风险，见 §5 ②）。
**回滚点**：§6.8 [2][4][6]、§7.1 [3]、§7.3 [7]、附录 C 第 9 项。

### A-10 允许重载（连带替全局未定项「函数重载」拍板） `⚠️ 越界决定`

**现状核对（重要）**：`nova-spec.md` §1.6 只排除了**运算符重载**；**函数/成员重载在 `nova-spec.md` 里没有任何条款**——既不在 §9 的未定清单里，也没有已定条文；仓库 `ref/docs/AGENTS.md` 的教学示例把「函数重载」标为 `?`。所以它是一个**没有落点的空白**，不是「已定未定项」。

**为什么本部分必须碰它**：① §6.4 [12]「模块级函数与成员函数的差别只有两点」把成员函数规则**反推**到模块级函数，于是「成员函数可重载」隐含地变成「函数可重载」；② 构造函数重载（§6.5 [2]）与显式拷贝构造（§6.5 [14]）依赖它；③ §7.8 [4] 把类型码写进符号名，明确是为重载服务的（「使**重载**（§6.4 [8]）在链接层可区分」）；④ §7.7 [7] 的导出元数据要带签名，用途写明「供跨模块重载解析与类型检查」。
**候选**：① 不允许重载（Rust 式：不同名字或类型别名）；② 允许，按**参数类型列表**区分、返回类型不参与（C++ 式，选定）；③ 允许但依赖默认参数 / 具名参数（§6.12 [12] 已排除默认参数）；④ 只允许构造函数重载。
**取舍**：① 在**无泛型**（§6.12 [5]）的语言里等于放弃「同一操作、不同参数类型」的统一命名，只能写 `sqrt_float` / `sqrt_double`，可写性与可读性双输；③ 与排除项冲突；④ 会让 `point_parse` 之类需要「同名不同参」的模块级函数无法写。② 的实现成本可控：本语言**没有隐式类型转换**（§2.1 强类型 + §2.6 的运算表），因此重载解析不需要「转换排名」这一整套最复杂的规则——候选集里只有精确匹配，多个匹配即歧义。
**选定**：§6.4 [8]（同一类内、或派生类相对基类可重载；参数类型列表不同；返回类型不参与；仅返回类型不同的同名同参函数为格式错误）、§6.4 [9]（只看静态类型精确匹配、多个同等匹配为格式错误）、§6.4 [12]（把规则推广到模块级函数）、§7.7 [7] + §7.8 [4]（跨模块可解析）。**这是越界决定**：需要回填 `nova-spec.md`（在 §9.3 新增「函数重载」条目并同时销掉，或在 §1.4/§5.5 附近新增条文；**已登记为正文附录 C 第 17 项**）。
**代价 / 风险**：
- 重载**解析算法**：报告初稿曾指出「正文只写了返回类型不参与区分」。**该缺口已在正文 §6.4 [9] 补上**：「只看实参**静态类型**的精确匹配、不引入重载专用隐式转换；多个同等匹配为格式错误」，与 §7.4 [6] 同调。剩余风险是它依赖「本语言没有隐式转换」这一前提，而 `int` ↔ `float` 的混合提升仍属 `nova-spec.md` §9.2 第 11 项未定——若将来引入提升，重载解析必须重新定义（精确匹配要改成「不差于」排序）。
- 派生类遮蔽规则（§6.6 [8]：同名不同签名 = 遮蔽整个基类重载集合，基类版本必须 `super.` 调用）是 C++ 的著名坑，需要文档与示例；有人会误以为「重载集合跨类合并」；跨模块重载解析要求编译器在编译单个模块时能读到**依赖模块的全部签名**（§7.7 [7]），这把「导出元数据的完整度」从「可选优化」变成「正确性前提」。
**回滚点**：§6.4 [8][11]、§6.5 [2][14]、§6.6 [8]、§7.7 [7]、§7.8 [4]、§6.12 [12]。

### A-11 `$` 前缀定为约定（不是语言规则）

**已定/未定**：`nova-spec.md` §9.3 第 4 项「`$` 前缀形参是规则还是约定」——正文 §6.4 [5] 销掉它；`01-语言设计.md` §8.4（`point.nova:8`）与 §10.A 第 14 条都记录了这个问题。
**候选**：① 语言规则：形参位上的 `$x` 自动绑定同名字段（需要新的语义规则，甚至新的绑定语法）；② 纯约定：`$x` 与 `x` 是两个不同标识符，因此天然不遮蔽字段（选定）；③ 禁止 `$` 出现在标识符里（需改 §1.1 / §1.2，均已定，排除）。
**取舍**：② 由 §1.2 的标识符产生式**直接推出**（`$` 可作首字符），语言不为其增设任何规则——完全符合「简洁性」；而且它给 `$` 这个「在字符集里但一直缺用例」的字符找到了第一个正当用途（速记第 9、11 行纳入 `$` 之后一直没派上用场）。① 需要把「形参名首字符 `$`」这一词法事实升级为语义绑定规则，还要定义「没有同名字段时怎么办」「`$` 前缀能不能用于局部变量」等一串问题。
**选定**：§6.4 [5]（`$x` 是约定，不是特殊语法；由 §1.2 推出）；与 §6.4 [4]（局部名遮蔽字段时必须写 `self.`）并存，因此「避免遮蔽」有两条写法。
**代价 / 风险**：
- **没有任何检查能抓住 `$` 的拼写错误**：把 `function __constructor__($x: float) { x = $x; }` 里的 `$x` 写成 `x`，编译器只会按普通标识符规则处理（自我赋值或未声明），不会提示「你是不是想写 `$`」。这是 ② 的固有代价（约定不产生诊断）。
- 同一件事（区分形参与字段）有两种风格：`$x`（point.nova）与 `self.x`（§6.4 [4]）。文档需要给出推荐风格，否则课程评审时会看到两种写法并存；对 C++/Java 背景的读者不直观（没有 `this.` 习惯的迁移路径是 `self.`，不是 `$`）。
**回滚点**：§6.4 [5]、§6.1 的示例（`point.nova` 风格）、附录 C 第 12 项（销掉 §9.3 第 4 项）。

### A-12 空类大小 = `vptr` 宽度
**候选**：① 0 字节（贴合 `nova-spec.md` §2.6「大小**视成员数量**」的字面：没有成员就是 0）；② `vptr` 宽度（选定）；③ 1 字节（C++ 的占位做法，保证地址唯一）；④ 0 字节 + 允许多个空白对象共享地址（用身份比较以外的办法区分对象）。
**取舍**：关键是「每个对象都必须携带 `vptr`」这一既成事实：§6.7 [5] 让所有 `public`/`protected` 非 `static` 成员函数天生可重写，因此**任何类**都可能有可分派函数，也就都需要 `vptr`。于是 ① 与 ④ 都不可行：`vptr` 放在偏移 0（A-3）且不能为 0 字节；`==` 是身份比较（§6.5 [15]），对象必须有唯一可区分的身份，④ 会让「两个不同的空对象」在身份上无法区分。③ 与 ② 相比没有优势（多出来的那 1 字节既不对齐也不够放 `vptr`）。候选 ⑤「无可分派函数的类不带 `vptr`」**曾被考虑并放弃**：§7.8 [6] 确实承认了「无基类、且没有任何可分派成员函数」的类可以按值传递（其布局 = 字段 + 填充，无 `vptr`）——但如果用户类按此规则省 `vptr`，那么「给这个类加一个 `public` 方法」就会**改变对象布局**，直接破坏 A-3 的二进制兼容取向。
**选定**：§6.11 [5]（空类大小 = `vptr` 宽度，对齐 = `vptr` 的对齐）、§6.11 [2]（`align(class) = max(vptr 对齐, 最大字段对齐)`；`size` 向上取整到 `align` 的整数倍）。
**代价 / 风险**：
- 与 `nova-spec.md` §2.6 的字面冲突（「视成员数量」），必须回填为「见正文 §6.11（含实现隐式加入的 `vptr`）」（正文附录 C 第 2 项已登记）；纯标记类（例如只用来做类型标签、只有静态成员的类）也要占一个指针宽度。
- 与 §7.8 [6] 的原表述（「无 vptr 的类可按值传给 C++」）曾与 §6.11 [1][5] 冲突（本报告 ②b 第 3 项）。**已在正文修订**：§7.8 [6] 该行改为「布局 = `vptr` 槽位 + 字段区；C++ 侧必须按目标 ABI 的 `vptr` 宽度声明等价 `struct`（首成员为指针宽度的占位槽），且**不得读写该槽位**；不愿依赖 `vptr` 宽度时按不透明句柄处理」。取舍是**保持「所有类对象都带 `vptr`」不变**——否则「给类加一个可重写方法」会静默改变其布局，与 A-3 的二进制兼容取向正面冲突；代价是这类对象不能直接当 C 风格 `struct` 用，原生包必须知道 `vptr` 宽度（§6.11 [7] 末尾已补「新增可分派函数 ⇒ 不兼容」作为前提）。
**回滚点**：§6.11 [2][5]、§7.8 [6]、§2.6 回填（附录 C 第 2 项）。

### A-13 无抽象成员的缺口（本部分识别出的规范缺口）

**现状**：缺口由正文附录 B B-3 第 3 项登记；排除依据 §6.12 [4]（抽象成员 / 接口 / `trait` / `final` 都不做）。
**候选**：① 不提供（选定）；② 纯虚成员：只声明不定义即「必须被重写」（类似 C++ 的 `= 0`）；③ 新增 `abstract` 关键字或 `interface` 声明；④ 只靠约定与文档（与 ① 是同一件事的两种表述）。
**取舍**：② 看起来最省，但**被 §6.4 [1] 堵死**：该条已经给「只声明、以 `;` 结尾的成员函数」指定了唯一含义——「必须在同一模块内用 `类名::函数名` 给出定义，否则为**链接期错误**」。若再让同一种写法兼表「抽象」，两种含义会在同一个语法形式上打架，且错误从链接期提前到「未重写」就必须有一套新的检查规则。③ 需要新关键字（§1.4 已封版）或新声明形式（与「简洁性」冲突）。①/④ 的代价是**完全没有编译期强制**。
**选定**：不提供（§6.12 [4]），缺口以「约定 + 文档」承担；附录 B B-3 第 3 项如实登记。
**代价 / 风险**：
- 基类无法强制派生类实现某个函数。**缓解因素（值得写进报告）**：本语言没有向下转换、没有 RTTI（A-5），因此「忘记实现」不会在运行时炸掉（不会有空函数指针调用），只会表现为**静默的空行为**——错误的可见性差，但不会 UB。这与 A-5 是同一取向的两面：宁可少能力，不要不可预测的失败。
- 若将来要补 `abstract`，**不能复用 §6.4 [1] 的 `;` 语法**，必须用关键字或 `interface` 声明；这是本条留给后续版本的最重要信息；「类当接口用」的用法无法表达契约，类的可替换性只能靠文档。
**回滚点**：§6.6 [11]、§6.12 [4]、§6.4 [1]、§6.14 `method_decl`；附录 B-3 第 3 项。

## 3. 模块部分的取舍（B-1 … B-9）

### B-1 模块 = 文件 / 包 = 目录，无 `module` / `package` 关键字

**现状**：`nova-spec.md` §9.1 第 2 项「`::` 与 `import` 的完整语法（包名解析、`uni` 组织方式）」未定；速记第 334 行「包体系关键字：`import` 引入包」、第 402 行「其他包体系的一些模块体系还没有确定」——**这正是第 7 部分要销掉的那条未定项**。
**候选**：① 文件 = 模块、目录 = 包，无关键字（选定）；② 显式 `module a.b;` 声明 + 文件映射（Java/Go 式）；③ 显式 `package` 声明；④ 一个文件多个模块（需分隔语法）；⑤ 模块 = 目录、文件 = 子模块。
**取舍**：① 零新增关键字（`module`/`package` 都不在 §1.4）；不会有「声明与文件路径不一致」这种错误类别（因为它根本不能声明）；`nvc` 一个文件一个编译单元（§7.1 [1]）与「无头文件 + 顶层默认导出」天然配套（B-3）；模块名进符号名（§7.8 [4]）后，文件路径即 ABI 的一部分，规则简单。②/③ 的价值是「一个文件能声明多个模块」与「不依赖文件名」，但与简洁性和工具实现量都不合。④ 需要一个文件内的分隔机制，且与「顶层声明互相可见」（§6.1 [4] 两遍扫描）冲突。
**选定**：§7.1 [1][2]（一个 `.nova` 文件 = 一个模块 = 一个编译单元；模块名 = 文件名去掉后缀；文件名必须是合法标识符；无 `module` 关键字）、§7.2 [1][2]（包 = 目录，包名 = 目录名；子包是子目录；限定名用 `::` 连接）。
**代价 / 风险**：
- 一个文件只能有一个模块 ⇒ 大文件不可避免；没有「内部模块」这种组织手段；**重命名文件 = 改模块名 = 改符号名**（§7.8 [4] 把模块名编进符号名）⇒ 破坏二进制兼容。工具（`nvp`）应当能诊断「符号名变了」，本版本没有规定。
- 目录名必须是合法标识符 ⇒ 不能用 `math-utils/`、`3rd-party/` 这类目录名（速记 §1.2 的标识符规则不允许 `-` 和数字开头）；跨平台大小写敏感性未规定（`Math.nova` vs `math.nova`）⇒ 建议进 §7.10 未定项（本报告 §7 补登）。
**回滚点**：§7.1 [1][2]、§7.2 [1][2]、§7.11 EBNF、§7.8 [4]（模块名进符号名）。

### B-2 包作用域并集，而不是强制三段限定名

**必须满足的硬证据**：课程既有示例 `eqroot.nova` 第 1 行 `import math;`、第 11 行 `let d = math::sqrt(b * b - 4 * a * c);`。`math` 是**独立包**（速记第 340 行「其他包 math 使用 import」、第 342 行「内置包无需路径解析，形如 math 不是内置的包需要 `math::` 路径解析」；`nova-spec.md` §7 同），而 `sqrt` 在文件系统里最自然的落法是 `math/sqrt.nova` 里的一个顶层函数。若规定「限定名必须是 `包::模块::名字` 三段」，那么 `math::sqrt` 只能被解释成「包 `math` 的模块 `sqrt`」并因缺名字而**格式错误**，课程示例当场失效。所以「包作用域 = 包内所有模块导出名字的并集」不是为了少打字，而是**为了既有示例能编译**。
**候选**：

| 候选 | `math::sqrt` | 歧义处理 | 示例改动 |
|---|---|---|---|
| ① 包作用域 = 模块导出名字的并集（选定） | 合法 | 歧义 ⇒ 要求 `包::模块::名字`，否则格式错误 | 无 |
| ② 强制三段 `包::模块::名字` | 非法 | 不存在（唯一） | `eqroot.nova` 必须改 |
| ③ 只允许 `import 包::模块;` 后用裸名 | 非法 | 冲突即格式错误，无消歧手段 | 示例必须改且无替代写法 |
| ④ 并集 + 就近猜/自动消歧 | 合法 | 猜（与 §7.4 [6] 冲突） | 无 |
**取舍**：① 保持既有示例零改动（这是课程评审的硬约束）；② 可写性好（短的限定名）；③ 与 §7.4 [6]「任何在编译期无法唯一确定的名字都是格式错误」同调：**歧义必须显式消解，不猜**；④ 与 ③ 的取向正相反，排除。实现上，并集只是**编译期**解析：`nvld` 的符号名始终带模块名（§7.8 [4]），所以并集不影响 ABI，只影响 `nvc` 需要建立「包 → 导出名字集合」的索引（这要求编译器能读到包内所有模块，与「下载源码现场编译」的既有结论相容）。
**选定**：§7.2 [4]（包作用域 = 导出顶层名字的并集，`math::sqrt` 可解析）、[5]（同名冲突 ⇒ 裸限定访问为格式错误，必须写 `包::模块::名字`）、[6][7]（同包内模块之间不需要 `import`，直接用 `模块名::名字`）、§7.3 [3]（`import 包;` 只让包名可解析，不引入裸名）、§7.4 [3]（限定名形式表）。
**代价 / 风险**：
- **本报告识别的缺口**：§7.2 [5] 只规定了「**两个模块导出同名顶层名字**」的冲突，**没有规定模块名与包内导出名字撞名**的情形——若 `math` 包里既有 `math/sqrt.nova`（模块 `sqrt`），又有某模块导出的函数 `sqrt`，`math::sqrt` 到底是哪一个？建议补一条：模块名优先（与 §7.4 [4] 第 3、4 步的「先本模块、后导入」顺序同构），或直接规定「包内模块名与导出名字不得同名（格式错误）」，或要求三段消歧。
- **依赖脆弱性**：并集让「包里有多少名字可用」变得不透明；依赖包升级时新增一个导出名字，可能与使用方的名字撞名而使**使用方**编译失败（§7.3 [5] 表：与本模块已声明名字同名即格式错误）。缓解：撞名只影响裸限定访问，可用三段形式消解；但使用方不一定知道是谁撞了谁。建议在 §7.4 的解析规则里加「歧义诊断必须列出两个候选的完整限定名」（实现建议，非规范）。
- 编译器必须扫描整个包才能解析一个限定名，编译期开销与「包内模块数」相关。
**回滚点**：§7.2 [4][5]、§7.3 [3]、§7.4 [3][6]。

### B-3 顶层默认导出 + `private`，无 `export`

**已定约束**：`export` / `extern` 关键字不要（`01-语言设计.md` §1.3 的排除表）；无头文件（`nova-spec.md` §7）。
**候选**：① 顶层默认导出，`private` 表模块私有（选定）；② 默认私有 + `export`（关键字已排除）；③ 用 `_` 前缀表私有（Python 风格，但 §1.2 允许 `_` 开头，约定不产生诊断，与 A-11 的 `$` 同类问题）；④ 在 `nvp.toml` 里列导出清单（把语言可见性挪到构建配置，可读性差）。
**取舍**：① 复用**已在关键字表内**的 `private`（§1.4 有 `private`/`protected`/`public`），零新增关键字；与类成员的访问组概念同名同构（都是「仅本级可见」），学习成本低；② 与排除项冲突；③ 没有任何强制力；④ 把语言规则放在语言外。① 需要一条配套的严格规则来兑现「无头文件」：模块私有的名字不得出现在导出接口中（§7.5 [4]），否则 `nvld` 无法只靠符号表链接。
**选定**：§7.5 [1]（默认导出）、[2]（`private` 前缀）、[3]（顶层写 `public`/`protected` 为格式错误——模块层没有继承关系）、[4]（私有名字不得作为导出函数/成员函数的参数或返回类型、不得作为导出类的基类或 `public`/`protected` 成员类型）、[5]（与类成员访问级别正交：先要求类可见，再按 §6.2 查成员）、[6]（编译期检查）。
**代价 / 风险**：
- 默认导出 ⇒ 不小心多导出（没有 `internal` 级别，也没有「包内可见」这一档）；`private` 只有「本模块一档」，对「同包其它模块可见」的需求（§6.2 [8] 明确没有「同包可见」旁路）无处表达；§7.5 [4] 的接口检查比「不检查」贵：实现必须在每个模块的导出面上做一次可达性/可见性扫描。这是无头文件必须付的代价，值得在报告里点明。
- `private` 在类里表示「仅本类」，在模块里表示「仅本模块」——同名不同域，文档需要并列说明（§7.5 [5] 的「正交」一词就是这个意思）。
**回滚点**：§7.5 [1][2][3][4][5]、§7.9 第 2 项、§7.8 [2][3]（`.novai` 里的可见性规则）。

### B-4 顶层无可执行语句 ⇒ 无初始化函数 ⇒ 循环 import 安全
**候选**：① 顶层只允许声明（选定）；② 允许顶层 `let`（需要模块初始化函数 + 静态初始化顺序规则 + 循环 import 的初始化顺序规则）；③ 允许顶层语句但禁止在循环依赖中初始化（Go 式部分初始化）；④ 顶层语句延迟到首次使用时执行（lazy，需要运行时支持）。
**取舍**：① 把「模块没有可变状态」变成一条**可以推理的语法事实**，于是三件事同时成立：运行时没有模块初始化函数；不存在静态初始化顺序问题；循环 `import` 天然安全（§7.3 [7]）——这三条还互相加强：静态字段初值必须是常量表达式（§6.8 [2]，A-9）也与它互为前提。② 会一次性丢掉全部三条收益。④ 需要运行时钩子与「首次使用」的判定，且与「无反射、无运行时名字查找」（§7.4 [7]）冲突。① 的损失很小：类声明与函数声明的值都是 `none`（§6.1 [5]），顶层表达式的值本来也没人接收。
**选定**：§7.1 [3]（顶层只允许 `import`、类、函数、`type` 别名、`const` 常量，以及它们加 `private`；其它可执行语句一律格式错误）、§7.1 [4]（无头文件）、§7.3 [7]（循环 import 合法）、§7.9 第 9 项。
**代价 / 风险**：
- 不能在模块顶层做「常量表初始化」这类事情，必须放进函数并由 `main` 调用（或使用常量表达式）。**这是可写性的真实损失**，尤其对本课程的 `uni` 标准库（例如字符分类表）。
- **本报告强调的真实缺口**：依赖包的「注册式」用法无法表达——原生包（§7.8，用 C++ 写）在真实系统里常常靠「加载时自注册」进入全局表；没有初始化函数 ⇒ 必须显式调用一个 `init()` 函数，或者干脆不做注册机制。本版本没有为此设计协议，属已知缺口。
- 模块级没有可变全局变量 ⇒ 需要全局可变状态时只能用类静态字段 + 显式 setter（`static total: int = 0;` 是常量初值，之后可以赋值，见 §6.8 [1] 的示例），这在单线程协作式模型下是安全的（C-1 的连锁收益）。
**回滚点**：§7.1 [3]、§7.3 [7]、§6.8 [2]、§7.9 第 9 项、§7.11 `module_unit`。

### B-5 两种 `import` 形式；无别名、无选择性导入、无传递可见性
**候选**：① 只提供 `import 包;` 与 `import 包::模块;`（选定）；② 增加 `as` 别名（需新关键字，§1.4 已封版）；③ 选择性导入单个名字 `import math::sqrt;`；④ 传递可见性 / 隐式重导出（`a` 导入 `b`，`b` 导入 `c` ⇒ `a` 能用 `c::`）。
**取舍**：① 与 B-2 配套：包作用域并集已经提供了短限定名，**对别名的需求下降**；③ 会让「`import` 的右操作数是包还是模块还是名字」需要三层消歧（`math::sqrt` 是模块还是函数？），与 B-2 的解析规则冲突；④ 会让「一个模块能看见什么」不再由它自己的头几行决定（可读性、可分析性下降，§7.3 [9] 的注就是这个理由），并且让循环 import 的可见面变得递归；① 明确把「消歧」的责任放在使用处（写限定名），规则只有一条。
**选定**：§7.3 [1]（两种形式）、[2]（所有 `import` 必须在模块最前面；顺序不影响解析结果但位置违规为格式错误）、[4]（`import 包::模块;` 引入裸名）、[5]（冲突规则表：与本模块声明冲突或与另一个模块导入的名字冲突 ⇒ 格式错误；与 `uni` 预导入同名 ⇒ 合法，遮蔽）、[6]（重复导入幂等）、[8]（解析失败是编译期格式错误，不是链接错误）、[9]（无传递可见性）、[10]（`import uni;` 等价于无操作）、[11]（无别名、无选择性导入）。
**代价 / 风险**：
- `import 包::模块;` 一次引入该模块**全部**导出名字 ⇒ 冲突只能改限定名（§7.3 [5]）；大型库里模块级「命名空间污染」无法从导入侧控制；没有别名 ⇒ 长限定名没有缓解手段（`graphics::render::canvas::...`）。
- `import` **不在 §1.4 的关键字表里**（正文附录 B B-3 第 1 项 / 附录 C 第 1 项）：这不是本部分的取舍，而是正文识别出的**全局缺口**，必须回填，否则词法层与模块层对不上；§7.3 [2] 要求 `import` 必须在最前，但 §6.1 [4] 又说两遍扫描与书写顺序无关——两条并不矛盾（顺序无关 ≠ 位置自由），但文档要讲清，否则读者会以为可以随便放。
**回滚点**：§7.3 [1][4][5][9][11]、§7.9 第 4、5、8 项、§7.11 `import_decl`、§1.4 关键字表（回填 `import`）。

### B-6 `uni` 唯一预导入与遮蔽规则

**已定约束**：速记第 336 行「I/O 包：`uni` 直接内置引用，不用显式 import」、第 340 行「其他包 `math` 使用 import」、第 342 行「内置包无需路径解析」；`nova-spec.md` §7「`uni` —— 标准包」「`math` —— 独立包，与 `uni` 平级」。未定部分：§9.1 第 2 项里的「`uni` 组织方式」。
**候选**：① `uni` 是**唯一**预导入包，其名字可被遮蔽，用 `uni::名字` 显式访问（选定）；② 允许第二个预导入包（如 `io`，速记第 346 行明确要求删掉 `import io`）；③ 预导入名字不可遮蔽（与用户名字冲突即格式错误）；④ 取消预导入，一律显式 `import uni;`。
**取舍**：① 与已定结论完全一致，且示例零改动（`println`/`print`/`input`/`range` 裸名：`sort.nova`、`eqroot.nova`、`point.nova` 都在用）；③ 会与「用户想写自己的 `print`」冲突，且遮蔽本来就是「最近者胜」（§7.4 [4]）的自然结果；④ 与已定结论冲突。① 还顺带把速记第 130 行「输入输出用包/库来做，**而不是内建的语句**」落实了：`print`/`println`/`input`/`range` 是 `uni` 的导出名字，正文只在 §7.6 [3] 给它们**语言级语义**（`{}` 占位与 `input` 的实参必须是可赋值的位置），而不是把它们变成语言语句。
**选定**：§7.6 [1]（唯一预导入包）、[2]（可遮蔽，被遮蔽后 `uni::名字`）、[3]（语言级入口表：`range(a,b)`、`range(a,b,j)`、`print`、`println`、`input`）、[4]（`range` 的迭代语义：左闭右开、循环变量是只读副本）、[5]（除 `uni` 外不得再有预导入包）。
**代价 / 风险**：
- `uni` 在实现上必须是编译器内建符号表（每个模块都可见），因此「`uni` 也是一个普通包」这句话带一个例外：它不能像其它包那样被依赖解析替换/缺失（§7.10 第 4 项：`uni` 内部模块划分未定，本报告在 §7 补一句）；遮蔽 + 无前导 `::`（§7.4 [5]）⇒ 想用被遮蔽的名字必须记得写 `uni::`；`::sqrt(x)` 是格式错误，没有「全局」捷径。
- `print(fmt, args...)` / `input(targets...)` 的**可变参数签名**没有类型系统支撑（本语言无泛型、无可变参数类型），正文只能在表里给形态；完整签名与错误约定属《标准库》部分（§7.10 第 4 项、§8.11 第 5 项）。**这是 `uni` 与第 7 部分之间最大的接口风险**（§5 ②）。
**回滚点**：§7.6 [1][2][3][5]、§7.4 [4][5]、§7.9、附录 C 第 12 项。

### B-7 `nvp.toml` / `nvp.lock`（本部分新增）

**现状核对**：`nova-spec.md` §7 只说「包管理实现：下载 C++ 源码，现场编译」；速记第 324 行只说「`nvp up` 指令：下载源码」；**清单文件与锁文件在四份文件里都没有出现过**。正文 §7.7 [2][3] 明确标注「（新增定义）」——这是第 7 部分**新增**的规范内容，不是对既有结论的展开。
**候选**：① TOML 清单 `nvp.toml` + 锁文件 `nvp.lock`（选定）；② 用 Nova 语法写清单（自举、风格统一，但清单要在没有编译器时被读取 ⇒ 引导问题，且需要为配置文件设计一个 Nova 子集）；③ 无清单，约定目录结构 + 环境变量；④ 只有清单、不要锁文件（无法保证可复现）。
**取舍**：① 一个文件同时描述项目、依赖、原生包声明（`[native]` 段），与「关注二进制兼容」（§2.2）配套的 `nova`/`abi` 字段有落点；③ 的可复现性与依赖声明都无处安放；④ 丢掉「清单 + 锁文件相同 ⇒ 解析结果相同」这条可复现构建保证（§7.7 [3]）；② 的自举价值在课程阶段不如「工具实现量」重要（TOML 是最小解析成本）。
**选定**：§7.7 [1]（工具链 `nvc` / `nvld` / `nvp`）、[2]（`nvp.toml`：`name` / `version` / `nova` / `src` / `[deps]` / `[native]`）、[3]（`nvp.lock`：精确版本 + 来源 + 内容校验和；可复现构建）、[4]（命令表：`up` / `add` / `remove` / `build` / `run` / `clean` / `list`）、[5]（依赖源码与产物在 `.nvp/`，布局实现定义）、[6]（构建流水线）、[7]（导出元数据内容）、[8]（同一包两个不兼容版本 ⇒ 依赖解析必须失败）。
**代价 / 风险**：
- TOML 是**语言之外**的格式 ⇒ Nova 工具链需要一个解析器（与「简洁性」有轻微摩擦，但换来可控的实现量）。若将来工具链自举，这是一个外人格式；版本约束语法未定（§7.10 第 3 项；`"1.2"` 暂按「兼容该次版本」理解）；注册表/分发协议未定（§7.10 第 2 项）——**这两项被列为阻塞实现**（附录 B-1 第 3 项），因为依赖求解器写不了。
- ABI 版本号方案未定（§7.10 第 5 项 / §7.8 [11]，附录 B-1 第 5 项）⇒ 原生包的链接准入判据暂无编号规则；§7.7 [8]「不允许同一 ABI 名字对应两个实现」是必须的（否则 §7.8 [4] 的符号名会在链接期撞车），但它把「版本求解」从体验问题升级为**正确性问题**：`nvp` 必须真的求解成功，不能靠「都装上试试」。
**回滚点**：§7.7 [2][3][4][5][8]、§7.10 第 2、3、5 项、§7.11 `manifest`、附录 C 第 4 项。

### B-8 原生包桥接契约（`.novai` + `_NV` 名字修饰 + 调用约定 + 所有权 + 无异常跨界）

**现状核对**：速记第 404 行把「原生包桥接契约」列为待解决问题之一；`nova-spec.md` §9.3 第 7 项「`nvp` 现场编译 C++ 的 ABI 细节」未定。已定部分只有一句：**包用 C++ 写、`nvp` 下载源码现场编译**（速记第 332 行、`nova-spec.md` §7）。正文 §7.8 把这一句补成可实现的契约。
**候选**：

| 候选 | 跨模块类型检查/重载 | 实现量 | 与「无头文件」 |
|---|---|---|---|
| ① `.novai` 接口文件（Nova 声明子集）+ 长度前缀修饰（选定） | 完整（签名进元数据） | 中（复用 `nvc` 的声明解析） | 一致（`.novai` 不是头文件：无函数体、只描述边界） |
| ② 直接解析 C++ 头文件 | 完整 | 高（要 C++ 解析器） | 冲突 |
| ③ 用 YAML/TOML 描述接口 | 完整 | 中（新格式 + 与 Nova 语法不同步） | 不一致 |
| ④ 只允许 C ABI（`extern "C"`，不修饰名字） | 无（无法区分重载/命名空间） | 低 | —（但与 A-10 冲突） |
| ⑤ 不桥接（只用 Nova 写包） | — | 最低 | 与已定结论冲突 |
**取舍**：① 的关键设计点是**名字修饰用长度前缀**：速记与 `nova-spec.md` 都没有任何修饰规则，本部分必须新造一套，而「下划线连接」会让 `enc(a)+enc(b)` 与 `enc(a_b)` 撞名（正文 §7.8 [4] 的注就是这个理由）。类型码进符号名是 A-10（重载）在链接层可区分的**唯一**手段，因此 ④ 被 A-10 间接排除。⑤ 与「包用 C++ 写」的已定结论冲突。② 与「无头文件」的取向相反，且把 C++ 的语法依赖引进工具链。
**选定**：§7.8 [1]（C++ 编写 + 现场编译）、[2]（每个原生包必须提供 `<模块名>.novai`，纯声明）、[3]（接口文件允许的内容；出现函数体/顶层语句/非导出名字为格式错误）、[4]（名字修饰规则：`_NV` + 长度前缀 `enc` + 类型码；成员函数带类名；静态字段用 `_NVG`；异步加 `A`）、[5]（调用约定：值类型按 C 约定传值；`&T`、类类型、`string`/`array` 按对象地址传递；返回 `void` 即 `none`）、[6]（可跨边界类型表）、[7]（内存所有权：Nova 引用只在本次调用期间有效，C++ 不得长期持有）、[8]（错误传播：C++ 异常不得跨越边界，跨边界传播为 UB，失败必须用返回值/输出参数）、[9]（原生函数不能 `async`；调用是可能阻塞的）、[10]（符号表来自接口文件 + C++ 编译产物）、[11]（ABI 版本覆盖范围：修饰规则、布局、`vptr` 宽度、任务表示）、[12]（安全边界：越过即失去类型安全与内存安全保证，必须在清单标注并列出）。
**代价 / 风险**：
- **名字修饰是全课程最贵的锁定项**：一旦对外发布，改名等于所有原生包与已编译模块全部重编。§7.8 [11] 用 ABI 版本兜底，但版本号方案本身还没定（§7.10 第 5 项）。
- **本报告识别的扩展风险**：§7.8 [4] 的类型码表**没有 `const` 位**——`&T` 与 `const &T` 映射到同一个符号名（`R<T>`）。若将来定下 `const &T` / `&T const` 的语义（§9.1 第 1 项）并希望它们能参与重载区分，符号名规则要扩展（新增类型码），属 ABI 变更。现在两条路都还开着，但必须记住这个耦合。
- 长度前缀只编码类型码：参数名、`const`、默认参数（不存在）都不参与；`async` 只加一个 `A`。这意味着**修饰名不是完整签名**，完整签名靠导出元数据（§7.7 [7]）；所有权规则（[7]）把「C++ 不得长期持有 Nova 对象」写成硬约束，但**无法检查**（C++ 侧不受规范约束，[12] 已声明）⇒ 这是一条靠纪律执行的规则，不是靠工具。
- 无异常跨界（[8]）要求原生包作者把每个导出函数都做成 `noexcept` 并手写错误码；与 C-9（无错误传播通道）叠加后，原生包的错误编码约定完全没有语言支撑（§8.11 第 5 项）；`string`/`array` 跨边界是不透明引用（B-9）⇒ 原生包不能用零拷贝方式读字符串内容，实用性受限。
- `native` 只能作为整体安全降级：清单里一旦有 `[native]`，该包的调用点就不再享有内存安全保证（[12]），而语言无法做局部标注（没有 unsafe 块）。
**回滚点**：§7.8 [4][5][6][7][8][11][12]、§8.7 [2][3][4]、§7.10 第 5、6、7 项、§7.7 [2]（`[native]` 段）、附录 B-1 第 5 项。

### B-9 `string` / `array` 的内部存储按不透明引用

**现状**：`nova-spec.md` §9.2 第 3 项（`string` 属于类类型还是特殊内置类型）、第 4 项（`array`/`string` 的 `internal_storage`：是否指针、几字节、可见性）都未定；`nova-types.yaml` 只给了 `attributes` / `operations` 的名字。
**候选**：① 跨边界按**不透明引用**，C++ 侧不得假设内部布局（选定）；② 在规范里固定内部存储布局（C++ 可直接读写字节）；③ 把 `internal_storage` 声明为接口文件里的字段，让 C++ 侧按字段访问。
**取舍**：① 的最大价值是**不阻塞**：§9.2 第 2、3、4 项可以继续悬着，而第 7 部分的桥接契约照样能落地——这是「把未定项隔离在不影响本部分的边界之外」的样板；同时 ABI 稳定（内部存储以后改了也不影响原生包）。②/③ 会把 `string`/`array` 的表示写进 ABI，之后任何优化（小字符串优化、共享缓冲区）都变成破坏性变更。① 与 `[index] -> reference`（`nova-types.yaml`）的关系也要说清：`[index]` 返回的是 Nova 侧的引用，等价于一个地址；但 C++ 拿到这个地址仍然**只能读写单个元素**，不能推出长度或缓冲区结构。
**选定**：§7.8 [6]（`string`/`array` 可跨边界，作为不透明引用，C++ 侧不得假设内部存储布局）、§7.10 第 7 项（内部存储跨边界的稳定化仍是未定项）。
**代价 / 风险**：
- 原生包无法做零拷贝的字符串/数组处理：只能用 Nova 侧成员函数逐元素访问，或复制到 C++ 容器（性能损失明确）；若将来固定布局，必须新增 ABI 版本（因为 §7.8 [11] 的 ABI 覆盖范围会扩展）。
- `string` 是否带 `vptr`（若 `string` 归为类类型则按 §6.11 [5] 带，若另设特殊内置类型则不一定）继续悬着 ⇒ 与 A-12 的代价里提到的问题**同源**：本规则对两种可能都成立，这正是选它的理由，但也意味着 §7.8 [6] 的「不透明句柄」与 §6.11 [1] 的布局规则之间还有一处需要对齐（见 §5 ②）。
**回滚点**：§7.8 [6]、§7.10 第 7 项、附录 B-2 第 2 项、§2.6 回填（`string` 行）。

## 4. 异步部分的取舍（C-1 … C-10）

### C-1 协作式单线程并发，而非速记/笔记提到的「支持多线程」 `⚠️ 与课堂提法相反`

**冲突与依据的完整核对**：
- `01-语言设计.md` §10.A 第 10 条（逐字）：「**`async` / `await` / `yield`**：课上提到「支持多线程」，但只有关键字、没有语义 —— 线程模型是什么（真线程 / 协程 / green thread）？」；`nova-spec.md` §9.3 第 3 项：「`async` / `await` / `yield` 的线程模型」——**明确标注未定**。
- 速记第 126 行：「`yield`：**为协程做准备**」（协程方向）；速记第 400 行：「完整异步与生成器体系没有确定」；结论：**「支持多线程」不是已定结论**，第 8 部分是对未定项的拍板；但「课上提过多线程」这件事必须显式说明被**偏离**了，不能默默不提（本条目就是说明）。
**候选**：

| 候选 | 数据竞争 | 多核 | 与「无原子类型/无锁」 | 实现量 |
|---|---|---|---|---|
| ① 真多线程 + 原子/锁（课堂提法） | 存在，且**无法在类型系统里表达或检查** | 可用 | 必须引入一整套同步机制 | 最高（含内存模型） |
| ② 协作式单线程 + 结构化并发（选定） | 结构性不存在 | 不可用 | 不需要 | 低（单线程调度器） |
| ③ 线程池 + green thread（隐式抢占） | 存在且更难推理（抢占点不可枚举） | 可用 | 需要 | 高 |
| ④ 单线程事件循环（无 `async` 关键字） | 不存在 | 不可用 | 不需要 | 中（但废弃已有关键字） |
**取舍**：② 的决定性理由是**可靠性**：速记第 372 行「类型安全，行为可预测 —— 错误尽可能在编译器暴露」。在 ① 里，共享可变状态的数据竞争既不能表达也不能检查（没有原子类型、没有所有权系统），等于把「不可预测」写进语言；② 用一条极简规则替代整套并发同步机制——**切换点是唯一可观察的交错位置**（§8.6 [1]），于是「不含切换点的代码段是原子的」（§8.6 [3]），程序可以依赖这一点而无需任何额外同步。③ 的抢占点不可枚举，比 ① 更难推理，且仍需要同步机制。④ 会废弃 `async`/`await`/`yield` 三个已定关键字（§1.4），且与速记第 126 行「`yield` 为协程做准备」不符。另外 ② 与 A-9（静态字段 = 全局可变状态）互相加强：单线程下 `static total = total + 1` 天然安全，多线程下就必须同步。
**选定**：§8.1 [3]（协作式：任一时刻至多一个任务运行）、[4]（不提供并行：无多线程语义、无原子类型、无锁；类类型是引用语义，多个任务可安全共享同一对象）、[5]（内存模型：共享内存视图、切换点构成 happens-before 边、无屏障/`volatile`/内存序）、[7]（不保证公平性）、[8]（无优先级、无取消、无超时）；§8.10 第 1、2、3 项。
**代价 / 风险**：
- 与课堂提法相反 ⇒ **必须老师确认**（§5 ① 第 2 项）。若翻盘为多线程，§8.1/§8.6/§8.7/§8.9 以及 §7.8 的 ABI 覆盖范围要全线重写；**无多核收益**：CPU 密集任务的上限锁死在单核（§8.9 [3]）。
- **一个不含切换点的死循环会永久占住调度器**（§8.1 [7]、§8.6 [6]）——比多线程更脆：多线程下别的线程还能跑，这里整个程序停住。这是 ② 最尖锐的代价。
- 「无数据竞争」的保证弱于「共享不可变」：对象仍然可以被多个任务修改（§8.1 [4] 的注），只是交错点被限定在切换点；因此「切换点之间是原子的」（§8.6 [3]）是一条**程序员必须记住**的规则，而不是类型系统强制的性质（没有 `const` 方法、没有所有权检查，见 A-6 的代价）。
- 将来若要并行：需要原子类型/锁 + 内存模型 + 调度器改造 + ABI 版本变更（§8.9 的表第 3 行已列为演进方向）。
**回滚点**：§8.1 [3][4][5][7][8]、§8.6 [1][3][4]、§8.9 [3]、§8.10 第 1、2、3 项、§7.8 [11]、附录 C 第 11 项（§9.3 第 3 项的销法要改写）。

### C-2 结构化并发（任务归作用域所有，作用域退出隐式等待）
**候选**：① 结构化并发：任务归创建它的作用域所有，作用域退出时隐式等待（选定）；② 自由飞行任务 + 显式 `join`（需要新的运行库 API 与任务句柄参数）；③ `detach`（后台任务，不做等待）；④ 只允许 `await` 立即等待（无并发，退化为顺序执行）；⑤ 结构化并发 + 作用域退出时**取消**剩余任务（与 C-8 的无取消冲突）。
**取舍**：① 与「无取消、无超时」（C-8）形成闭合——**如果没有取消，又允许自由飞行任务，那么程序退出时必然存在「无人等待的任务」**，需要一种「等全部任务」的收尾机制；结构化并发把这个问题从「运行库 API」变成「语言语义」，于是 `main` 完成 ⇒ 所有任务已结束（§8.8 [4]），不需要 detach/join 这类 API。它还与 C-3（任务类型不可书写）天然咬合：句柄不能传参、不能存字段 ⇒ 句柄的作用域**必然**就是创建它的作用域，结构化并发只是把这个事实语义化。② 需要句柄作参数（C-3 禁止）或者一个「等所有任务」的隐式 API；③ 在无取消的语言里会让程序退出时的行为不可定义（要等？不等？）；⑤ 与 C-8 冲突。④ 会消掉并发的全部意义。
**选定**：§8.2 [7]（作用域结束时运行时等待该作用域内创建且尚未结束的任务；离开方式包括正常结束、`return`、`break`/`continue` 离开循环体）、[8]（因此异步调用可以直接作为语句丢弃句柄，句柄丢弃不影响任务归属）、§8.8 [4]（`main` 完成 ⇒ 无残留任务 ⇒ 无需「等待后台任务」的 API）。
**代价 / 风险**：
- **无法表达长期后台任务**（常驻监听、守护任务）：这是真实的能力缺口，本版本没有替代（只能在 `main` 里用循环保活）。§8.10 第 4 项把 detach 列为排除项；隐式等待 ⇒ 可能出现「未预期的阻塞」：`break`/`continue` 离开循环体也会触发等待（§8.2 [7] 明确列举），写循环的人未必意识到；错误表现为「程序在某处卡住」，而语言没有超时/取消（C-8）可以救。文档必须显式举例。
- 等待的**顺序未规定**（只保证「全部完成」）：用户不能依赖完成顺序，与 §8.1 [7]（不保证公平性）一致，但没有单独条款说明，建议在 §8.2 [7] 补一句（本报告 §7 补登）。
**回滚点**：§8.2 [7][8]、§8.8 [4]、§8.9 [2]、§8.10 第 4 项。

### C-3 无泛型下的 `Task⟨f⟩` 单态化 + 任务类型不可书写

**现状**：本语言无泛型（§6.12 [5]）；无异常（全局已定）；无向下转换（A-5）；无可空类型（§8.9 [1] 注）。
**候选**：① `Task⟨f⟩` 按被调用函数**单态化**，类型不可书写、只能作局部变量（选定）；② 统一任务类型 `Task`（无结果类型参数）；③ `Task[T]` 泛型任务类型（§8.10 第 7 项）；④ 没有任务值：`await` 只能直接作用于调用表达式（`let x = await f();`），禁止「先启动后等待」。
**取舍**：④ 会消掉「先启动多个、再依次等待」这一唯一的并发组合方式（§8.2 [8] 的 `fan_out`），等于把并发能力砍掉一半；② 无法回答「`await t` 的结果是什么类型」——若用运行时装箱，取结果就需要向下转换，**被 A-5 直接堵死**（这是 ② 被排除的决定性理由，值得记录）；③ 无泛型，排除。① 是「无泛型语言如何表达带结果类型的句柄」的标准答案：按函数单态化、每个异步函数一个任务类型（零装箱、零转换）；而「类型不可书写」不是额外的限制，而是**唯一自洽的选择**——一个「元素类型取决于函数」的类型在无泛型下无法命名，因此也就无法出现在形参、返回类型、字段、`type` 别名或数组基类型里（§8.2 [6]）。
**选定**：§8.2 [5]（任务句柄静态类型记作 `Task⟨f⟩`，按函数单态化）、[6]（类型不可书写：不得出现在形参/返回/字段/`type` 别名/数组基类型；只能由 `let` 推导为局部变量）、§8.10 第 6、7 项。
**代价 / 风险**：
- 任务句柄**只能作局部变量** ⇒ 无法写「等待任意任务」的通用工具（如 `await_all`），无法把未完成的工作存进对象（§8.5 [6]）、无法放进数组；§8.9 [2] 的「并发组合只能用先启动后依次 `await`」就是这么来的。
- `Task⟨f⟩` / `Stream⟨f⟩` 使用了 `⟨⟩` 记号，而 §1.6 的运算符集里**没有**这个符号。正文用「记作」的措辞并声明不可书写，所以它**不需要进运算符表**（§8.12 的 EBNF 也只把这些形式列为格式错误）——这是「类型不可书写」带来的一个隐性收益：源程序里不出现这种类型，词法/语法层完全不必支持它。但报告要写清这一点，否则评审会问「`⟨⟩` 是什么」。
- 单态化会让每个异步函数产生一个任务类型 ⇒ 元数据、调试信息与实例化数量随异步函数数量增长（实现细节，本版本不规定）；与 A-5 的耦合：一旦将来引入向下转换或装箱任务，② 就重新变成可行方案；反之若引入泛型，③ 是自然演进（§8.10 第 7 项），当前设计不封锁它。
**回滚点**：§8.2 [5][6]、§8.5 [6]、§8.7 [3]、§8.9 [2]、§8.10 第 6、7 项、§8.12。

### C-4 `await` 只作用于任务表达式；只有 async 函数能调用 async 函数（函数着色）
**候选**：① 静态着色（选定）：`async` 必须显式标注并沿调用链传播；② 隐式等待：普通函数调用 async 函数时自动阻塞等待；③ 对称协程（不区分 async，任何函数都能挂起）；④ 提供 `block_on`/`join` 阻塞原语，普通函数可显式等待；⑤ 关于「异步调用点本身算不算切换点」：算（选定，§8.6 [2] ④）／不算（新任务只入队，最早在调用者的下一个切换点之后才可能运行）。
**取舍**：② 需要一个「阻塞当前任务」的原语，而在**单线程协作式**模型（C-1）下，「阻塞当前任务」= **整个程序停住**（没有其它线程可以推进）⇒ 隐式等待的后果比多线程语言严重得多：一句看起来无害的调用就能让全部任务停摆，且程序员看不出哪里是阻塞点。这条与 C-1 是强耦合的：**多线程下 ② 尚可讨论，单线程下 ② 不可接受**。③ 无 `async` 标注时，「这个函数会不会挂起」无法从签名看出，且实现上调用者仍必须能挂起（着色其实是实现约束的语言投影）。④ 是最接近 ② 的方案，但同样把「阻塞整个程序」变成显式操作，且会让「切换点清单」（§8.6 [2]）多出一项；正文在 §8.2 [10] 的注里明确说「本语言没有阻塞原语（没有 join/block_on）」。⑤ 选「算」而不是「不算」，是为了让「可能交错的位置」**仍然可枚举**（§8.6 [1]）：如果把调用点排除在清单外，新任务在何时第一次推进就变成不可枚举的隐式交错点，比承认它更糟；代价是「启动点也不再原子」，因此**可移植的写法是「先启动、后等待」**（§8.2 [8]、§8.6 [3] 的注）。
**选定**：§8.2 [10]（异步调用只能出现在异步函数体内，违反为格式错误）、§8.3 [2]（`await` 的操作数必须是任务类型表达式）、[3]（`await` 只能出现在异步函数体内）、[5]（`await` 不做错误传播）、§8.6 [2] ④（异步调用点是切换点）+ [3]（原子段不含 `async` 调用）。（「任务开始推进到哪一步」仍属实现定义，§8.2 [4]；程序不得依赖，附录 F-3 第 6 项。）
**代价 / 风险**：
- **函数着色**是 `async`/`await` 模型的固有代价（§8.9 [4]）；一旦库的下层改成 async，上层全部要改。C++、Rust、Kotlin、Python 同样如此——报告要点明这不是 Nova 的实现缺陷，而是该模型的性质。
- 构造函数不能 async（§8.5 [2]）、钩子不能 async（§8.5 [4]）⇒ 类无法在构造过程中做异步 I/O，只能「构造 + 异步 `open()` 静态工厂」两步（§8.5 [1] 的 `loader::open` 就是这个模式）。这是设计上的一个真实不便（对象无法「构造完成即就绪」）。
- 原生函数不能 async（§8.7 [3]）⇒ 所有原生调用都落在阻塞点上（C-7）；`main` 必须能是 async，否则异步功能在程序里无法使用（见 C-10）。
- 异步调用点是切换点（§8.6 [2] ④）⇒ **「启动」与「等待」必须分开写才是可移植的**（§8.6 [3] 的注）；如果依赖「启动之后调用者还独占执行」，程序在别的实现上就会失效（附录 F-3 第 6 项把「依赖推进速度」列为 UB）。
**回滚点**：§8.2 [10][11]、§8.3 [2][3][5]、§8.5 [2][4][6]、§8.10 第 8、9 项。

### C-5 `yield` 限定在 async 函数 ⇒ 生成器 + `Stream⟨f⟩`

**已定**：`yield` 是已定关键字（§1.4）；速记第 126 行「`yield`：为协程做准备」。
**候选**：① 含 `yield` 的 **async** 函数即生成器，调用返回 `Stream⟨f⟩`（选定）；② 独立的生成器关键字（`function*` / `generator function`，需新关键字，§1.4 已封版）；③ 同步生成器（`yield` 允许出现在普通函数里）；④ 双向生成器（`yield` 有返回值，消费者可回传）。
**取舍**：② 与关键字封版冲突。③ 看起来更通用，但语义上会变成「迭代器协议」——调用一个含 `yield` 的普通函数必须返回某种可迭代对象，而**该对象的类型是什么**？在无泛型下又要造一套单态化类型（C-3），而且普通函数不能 `await`，所以同步生成器里不能做并发。① 更省：把生成器归入 async 家族后，`Stream⟨f⟩` 与 `Task⟨f⟩` 共用同一套单态化机制（C-3），生成器体内可以 `await`（§8.4 [11]），`for` 迭代语法直接复用（§8.4 [5]）。④ 需要为 `yield` 定义一个值类型，并定义「消费者回传」的语义与错误路径（无异常、无可空类型 ⇒ 又是一条新的失败通道），本版本明确砍掉（§8.4 [4]：`yield` 的值是 `none`）。
**选定**：§8.4 [1]（含 `yield` 的异步函数是生成器）、[2]（返回类型注解 = 元素类型）、[3]（`Stream⟨f⟩` 不可书写、只能局部变量）、[4]（`yield` 是表达式，值为 `none`）、[5][6]（用 `for` 消费）、[8]（执行到末尾或 `return;` 即结束）、[9]（`break` 提前退出后生成器不再被恢复）、[10]（流是一次性的）、[11]（生成器体内可 `await`）、[12]（`yield` 出现在非 async 函数体内为格式错误）。
**代价 / 风险**：
- **普通函数里无法用 `yield` 写惰性序列**；`sort.nova` 那种普通函数只能靠 `range`（见 C-6）；流是**一次性**的（§8.4 [10]）：已耗尽的流再次迭代**静默结束**（不报错）。在无异常的语言里，这是一个静默失败点；`for s in squares(3)` 写两次，第二次什么都不发生。
- `break` 退出不触发清理（§8.4 [9]）——与 A-7（无析构）一致，但意味着生成器持有的资源只能靠运行时回收，不能靠用户代码；迭代异步流的 `for` **必须**在 async 函数体内（§8.4 [7]）⇒ 又一处函数着色的传播。
- 与 §8.6 [2] 的切换点清单耦合：取流元素是切换点，于是「`for` 迭代异步流」整体不是原子的，循环体的每次回边都可能交错——这一点与 `range` 循环（同步、原子）形成鲜明对比，是本语言最需要讲清的一对概念。
**回滚点**：§8.4 [1][3][4][7][12]、§8.6 [2]、§8.12、§8.10（若引入双向通道需新增条目）。

### C-6 同步序列（`range`）与异步流分离

**必须满足的硬证据**：`sort.nova` 的 `select_sort` 与 `print_arr` 都是**普通函数**，函数体里写 `for i in range(0, n - 1)`（`sort.nova:7`）/ `for i in range(0, a.length())`（`sort.nova:22`）。若把所有 `for 变量 in 表达式` 一律当作异步迭代（切换点 + 只能在 async 函数内），**既有示例全部非法**。因此「两类可迭代对象」不是风格问题，而是为了既有示例能编译。
**候选**：① 区分**同步序列**（`range`）与**异步流**（生成器），只有后者是切换点、只有后者要求 async 上下文（选定）；② 所有 `for in` 都是异步迭代（示例非法）；③ 让 `range` 也返回流（`range` 变成异步的 ⇒ 普通函数里不能用，同样破坏示例）；④ 用不同的关键字区分（如 `for await`，新语法）。
**取舍**：① 语义清晰：`range` 是编译期可知的计数循环（§5.3 的既有语法，`nova-spec.md` §5.3 已定），生成器是协程；两者恰好对应「原子代码段」与「切换点」的分界（§8.6 [3] 明确「所有 `range` 循环」属于原子段），这条分界与 C-1 的可靠性论证直接相连。②③ 破坏示例；④ 新增语法（简洁性）。① 还有一个好处：本部分**不必先统一迭代协议**——`array`/`string` 能否直接 `for` 迭代被明确留成未定（§8.11 第 4 项 / 附录 B-2 第 3 项）。
**选定**：§8.4 [7]（迭代异步流的 `for` 必须在异步函数体内；迭代同步序列的普通 `for` 不受此限制，也不是切换点）、§8.6 [2]（切换点清单共四项，其中「取流元素」针对异步流、「异步调用点」是另一项；[3] 明确「所有 `range` 循环」是原子的，并把 `async` 调用排除在原子段之外）、§7.6 [3][4]（`range` 的语义与左闭右开、循环变量是只读副本）、§8.11 第 4 项（`array`/`string` 是否可直接 `for` 迭代留作未定）。
**代价 / 风险**：
- 语言里有**两类**「可迭代」概念（同步序列 / 异步流），术语与文档成本上升：`range` 不是「流」，生成器才是；`for` 的语义取决于被迭代对象的类别——这是本部分最容易被读者误解的一处；`array`/`string` 的迭代方式悬空 ⇒ 用户需要先记住「哪些能 `for`」。**不阻塞**（可用 `range` + 下标，既有示例都是这么写的），但它是标准库设计的前置项。
- 若将来要把 `array`/`string` 纳入同步序列：只需在 §5.3 补条款并说明「实现靠 `length()` + `[index]`」，**不改切换点语义**，风险低。这也是把它留成未定项而不是现在拍板的原因。
**回滚点**：§8.4 [7]、§8.6 [2][3]、§8.11 第 4 项、§7.6 [3][4]、§5.3（回填）。

### C-7 原生调用 = 阻塞点，而不是切换点
**候选**：① 原生调用是**阻塞点**：调用期间调度器不推进任何其它任务，整个程序停在该调用上（选定）；② 原生调用是**切换点**（调用前让出、返回后继续排队）；③ 把原生调用卸载到线程执行（真并行）；④ 禁止在 async 函数里调用原生函数。
**取舍**：② 表达不了——「切换点」意味着「任务可以在此挂起、其它任务继续推进」，而原生调用是**同步返回**的（§7.8 [9]：原生函数不能 `async`），所以让出之后仍然要等它返回，没有收益只有复杂度。③ 与 C-1 直接冲突（真并行 ⇒ 需要原子类型与锁）；但要注意 ③ 恰恰是**将来最可能的演进方向**（§8.9 的表第 5 行、§8.6 [4] 的注都写了「允许标注可卸载的原生调用 + 原子类型」）。④ 会让原生包（本课程的标准库实现方式，速记第 332 行）无法在异步程序里使用，代价过大。① 的决定性理由是**不破坏 §8.6 [3] 的原子性承诺**：语言没有原子类型与锁（§8.1 [4]），如果原生调用能与其它 Nova 任务并行，共享对象的访问就不可控了——这正是 C-1 想避免的东西，不能在原生边界上漏回来。
**选定**：§8.6 [4]（原生调用必须当作阻塞点；调用期间调度器不推进任何其它任务）、§7.8 [9]（原声函数不能 `async`；Nova 侧的调用是可能阻塞的）。
**代价 / 风险**：
- **阻塞式 I/O 会冻结整个程序**（§8.9 [5]）——这是本版本**最大的实用性代价**：一个 `read()` 就让所有任务停住，「并发」在 I/O 场景下几乎失效（并发只能在纯计算任务之间体现）；不能用「原生包内部起线程」绕过：原生包不受规范约束（§7.8 [12] 已声明越过边界后安全保证不再成立），但那样做等于在语言不知情的情况下引入并行，与 C-1 的可靠性论证冲突。这一点必须在文档里明确劝阻。
- 扩展路径已在正文里写明（§8.6 [4] 的注）：引入显式并行的原生调用标注 + 原子类型。这条**必须与 C-1 的多线程演进一起做**，单独做会在语言里留下不可检查的并行源。
**回滚点**：§8.6 [4]、§7.8 [9]、§8.9 [5]、§8.9 的表第 5 行、§8.1 [4][5]。

### C-8 无任务取消 / 无超时 / 无优先级
**候选**：① 全部不提供（选定）；② 协作式取消标记 + 取消点（新 API + 新切换点）；③ 超时（需要定时器 + 可能需要在 `uni` 里加 `sleep`）；④ 优先级（调度策略的一部分）；⑤ 结构性取消（作用域退出时取消剩余任务）。
**取舍**：⑤ 与 C-2 的结构化并发**看似配套**（作用域退出时取消而不是等待），但它需要先把「取消」定义成一个**可观察事件**（任务必须有机会在切换点检查取消标记），于是取消点变成新的切换点，§8.6 [2] 的「完整清单」（现为四项）还要再增一项；同时「被取消的任务的结果怎么办」在无异常、无可空类型（C-9）的语言里没有表达方式。② 同理。③ 需要定时器与运行时事件源，而调度器实现本身还没定（§8.11 第 2 项），且 §8.11 第 6 项「`uni` 是否提供 `sleep`/定时器」也未定。④ 在「不保证公平性」（§8.1 [7]）的前提下意义有限。
**选定**：§8.1 [8]（本版本没有任务优先级、没有任务取消、没有超时机制）、§8.9 [2]（不提供取消、超时、优先级、detach、任务组、组合子）、§8.10 第 4 项。
**代价 / 风险**：
- 永远挂起的任务无法被中断或回收：两个任务互相等待 ⇒ 程序挂起（§8.3 [7]、§8.6 [6]），**没有任何恢复手段**；`main` 任务挂起则程序永不退出（§8.8 [6]）；没有超时 ⇒ 所有可能长时间阻塞的操作只能在库层面自带超时参数（约定，非语言机制；§8.11 第 5 项）。
- 无 detach 与 C-2 的结构化并发是同一决定的两面：报告要把这条说清，否则读者会以为「忘了做 detach」而不是「为了闭合语义而砍掉」；「无公平性 + 无取消 + 无超时 + 死循环占住调度器」四条叠加起来，本版本的并发程序**很容易写出永久卡住且无法诊断的形态**；这是 C-1 选型的连带代价，值得在课程评审时明确承认。
**回滚点**：§8.1 [8]、§8.3 [7]、§8.6 [2][6]、§8.9 [2]、§8.10 第 4 项、§8.11 第 6 项。

### C-9 无错误传播通道

**现状**：无异常（全局已定，速记第 18 行「不考虑异常」）；无可空类型（§8.9 [1] 的注引 §1.5：`none` 是 `void` 的值，不是「空的可选值」）；无泛型（§6.12 [5]）。
**候选**：① 用返回值编码失败（负数 / 状态值 / 输出参数，选定）；② 输出参数 `&T` + 返回 `bool`（选定方案的一种具体形式）；③ 引入可空类型 `T?`；④ 引入 `Result` 风格类型（需要泛型）；⑤ 引入异常（全局排除）；⑥ 引入一个「错误码枚举」（本语言无枚举，速记「枚举：不要」⇒ 只能用 `static const int`，正好用到 A-9）。
**取舍**：① 不引入任何新类型/新语法，与全局结论（无异常）一致，且与 `await` 的语义相容（§8.3 [5]：`await` 不做错误传播）；③ 会与 `none` 的定位正面相撞——速记第 92 行写「`none`：用于标识 null/nullptr」，而 `nova-spec.md` §1.5 明确「`void` 是类型，`none` 是该类型的值」；要做可空类型必须**先裁决这个冲突**（这是报告要提醒的关键点：③ 不是「加个语法糖」，而是要先改 §1.5/§2.1 的一条已定结论）；④ 无泛型，排除；⑤ 与「无异常」全局结论冲突。
**选定**：§8.9 [1]（`await` 不会失败、不传播错误；异步函数的失败必须通过返回值表达；调用者必须显式检查）、§8.3 [5]、§6.5 [12]（构造失败用 **输出参数 + `bool` 状态返回值**的静态工厂函数表达，例：`function point_parse(s: &string, result: &point) -> bool;`）。
**修订说明（第二轮评审 P1-4 后同步）**：本节原先把 `function point_parse(s: &string) -> point;` + 「失败返回 `none`」当作选定方案，**该写法已废弃**——`none` 是 `void` 的值（`nova-spec.md` §1.5），让 `-> point` 返回 `none` 等于引入空引用，与 §6.3 [4] 冲突。现行正文（§6.5 [12]、§8.9 [1]）按结果类型分三种情形给出手段：

| 结果类型 | 失败如何表达 | 条款 |
|---|---|---|
| 值类型（`bool`/`char`/`int`/`float`） | 哨兵值或状态编码（如 `-1`） | §8.9 [1] |
| 类类型 | **输出参数 `&T` + `bool`**（类类型无空值） | §6.5 [12]、§8.9 [1] |
| `void` | 只能靠输出参数 | §8.9 [1] |

**代价 / 风险**：
- **没有统一的失败表达**：每个库自己约定（哨兵值？状态值？输出参数？）。本语言连枚举都没有，状态码只能用 `static const int`（A-9）拼出来。这是可靠性上最实质的缺口；**忘记检查返回值不会有任何提示**（没有 `must_use` 之类的机制）⇒ 静默错误。
- **类类型的失败接口形态笨重**：调用方必须先构造一个占位对象再传引用（§6.5 [12] 的例子用 `point(0.0, 0.0)`）。根因是「无空值」与「无可空类型」两条已定/未定结论叠加——**这是本版本最尖锐的表达力缺口**（正文附录 B B-3 第 4 项已登记）。
- 与 `[index]` 越界行为（`nova-spec.md` §9.2 第 8 项未定）同类：错误通道缺失会把问题推给库约定与 UB。
- 与 C-3 的耦合值得记录：如果将来引入 `Result`/可空类型，**任务的结果类型也要跟着变**（任务类型需要第二个参数），即 `Task⟨f⟩` 的单态化形态会被迫升级为泛型任务类型——这正是 §8.10 第 7 项预留的演进方向。

### C-10 `main` 可为 async

**已定/未定**：`nova-spec.md` §9.1 第 5 项「`main` 签名与返回值语义」**阻塞规范定稿**；`01-语言设计.md` §10.A 第 7 条同。
**候选**：① `main` 可以声明为 `async function main() -> int`（选定）；② `main` 只能是普通函数；③ 运行时始终启动调度器（普通 `main` 也在任务里跑）；④ 由 `nvp.toml` 指定一个异步入口函数（入口名可配）。
**取舍**：② **不可行**——§8.2 [10] 禁止非 async 函数调用 async 函数，而语言又没有阻塞原语（§8.2 [10] 的注、C-4），因此若 `main` 不能是 async，**异步功能在整个程序里根本无法使用**（除非靠原生/运行时入口绕过，那等于另开一条通道）。③ 会把「普通 `main` ⇒ 程序里没有任务 ⇒ 不需要调度器」这一简化（§8.8 [2]）丢掉，且普通程序的启动成本增加。④ 把入口名变成构建配置，与 §7.1 [5]「根模块必须提供名为 `main` 的函数」的简洁规则冲突。① 保留两条路径：普通 `main` 零额外机制，`async main` 启动调度器并驱动主任务（§8.8 [3]）；与 C-2 的结构化并发配合后，`main` 任务完成时其作用域内任务都已结束，退出码就是 `main` 任务的返回值（§8.8 [4] 的推论）。
**选定**：§8.2 [11]（`main` 可以是异步函数）、§8.8 [1][2][3]（根任务执行 `main`；普通 `main` 按同步语义、返回值即退出码、此时程序内不创建任务；异步 `main` 由调度器驱动至完成，返回值即退出码）。这连带销掉 `nova-spec.md` §9.1 第 5 项的一部分（无参、返回 `int`、退出码、可为 async；回填项见正文附录 C 第 7 项）。
**代价 / 风险**：
- 有两条执行路径（有/无调度器），实现必须都覆盖；「程序里有没有任务」取决于 `main` 的修饰符，文档需要显式说明；`main` 的其余签名细节**仍未定**：命令行参数、是否提供 `args`（正文附录 B B-3 第 2 项）。这是一个会被课程评审问到的缺口。
- 死锁的后果：`main` 任务永远挂起 ⇒ 程序永不退出（§8.8 [6]），且无超时/取消（C-8）可以救。
- 与 §7.1 [5]（根模块必须提供 `main`）的边界：§7.1 [5] 把 `main` 的签名与退出码语义指向 **§8.2 [11] 与 §8.8**，本部分定的正是这两处；`main` 的其余细节（命令行参数）仍属附录 B-3 第 2 项的缺口。
**回滚点**：§8.2 [11]、§8.8 [1][2][3][4]、§7.1 [5]、附录 C 第 7 项。

### ②g 第六轮（独立评审）发现的问题及处置（**均已修进正文**）

> 本轮的三项都指向同一件事：**「受限产生式」要把非法边界写死在语法里，就必须把每一条约束都写全**。
> 上一轮补了构造/静态成员/去 `async`，但没有同时处理「构造函数名的词法二义」与「静态字段的类型范围」，
